# Argument schemes

A scheme is a template that turns confirmed facts into an argument: a claim, its
premises, the evidence each premise needs, what it attacks, and the rebuttals the
insurer is known to raise against it.

`backend/app/argumentation/schemes/*.yaml`, versioned by the `VERSION` file in
that directory and recorded as `schemes_version` on every argument graph.

## How a tier is decided

The three tiers are **computed**, never assigned:

- **Solid ground** — in the grounded extension. Every attack on it is itself
  defeated, so it holds on any reading.
- **Worth adding** — in some preferred extension but not the grounded one. It
  holds on some readings and not others.
- **Left out** — in no preferred extension. Kept visible so the user can see it
  was considered.

### The modelling decision that produces the middle tier

A scheme's `known_rebuttals` become real arguments in the framework, and each one
is placed in a **mutual** attack with the argument it answers.

That mutuality is deliberate. A known rebuttal is what the insurer *might* say,
not a fact. A one-way attack would defeat the counter-argument outright and the
user would be told their argument is dead when it is merely contestable. A mutual
attack yields two preferred extensions — one where the argument holds, one where
the rebuttal does — so the argument is credulously but not sceptically
acceptable. In the product's words: the insurer has a fair answer to this one, so
it is useful extra weight rather than your main point.

Attaching the evidence named in `defeated_by_evidence` adds an argument that
attacks the rebuttal one-way. That breaks the cycle, and the solver — not the
application — is what notices the argument has become Solid ground.

## Two rules for anyone adding a scheme

1. **Every scheme needs at least one known rebuttal.** Without one it cannot be
   contested, so the solver has nothing to compute and the tier becomes a label
   rather than a result. Asserted by a test.
2. **Every rebuttal needs `defeated_by_evidence`.** A rebuttal with no answer is
   a dead end: the user is told the insurer has a reply and given nothing to do
   about it. Also asserted by a test.

## A standing caution

A scheme encodes the *shape* of a legal argument, not a legal standard. Where a
`claim_template` asserts what a regulation or a plan document requires, that
assertion needs the same treatment as a deadline: a transcribed source, a
citation, and a `verified` flag. `strength: strong` is advisory metadata about
how the argument fares against its own known rebuttals. It is **not** a
prediction about any case, and the solver ignores it.

## Fields

| Field | Meaning |
|---|---|
| `id` | Stable identifier. Appears in letters as a paragraph's `argument_node_id`. |
| `denial_reason` | The `DenialReason` this scheme answers. |
| `side` | `patient`. The insurer's own reason is generated by the builder, not written here. |
| `claim_template` | The assertion, with `{service}`, `{insurer}`, `{condition}`, `{state}` placeholders. |
| `premises` | Each with `id`, `text`, and the `evidence` key that establishes it. |
| `attacks` | What this argument attacks, and how: `rebut`, `undermine` or `undercut`. |
| `known_rebuttals` | What the insurer says back. Each becomes a counter-attacking argument. |
| `strength` | `strong` or `conditional`. Advisory only. |
